# PIPELINE.md

## 1. 백엔드 파이프라인 단계별 설계

해커톤 타임어택과 자원 효율을 고려하여, 모든 AI 처리는 `gemini-4-argon` 단일 모델로 수행하며 API 호출을 최적화합니다.

| 단계 | 모델 (Argon) | thinking_level | 입력 | 출력 형식 | 예상 소요 시간 | 실패 시 처리 (Fallback) |
| --- | --- | --- | --- | --- | --- | --- |
| **1. 입력 검증** | -- | -- | 유튜브 URL | 유효성 결과 및 캐시 키 | < 1초 | 유효하지 않은 URL 거부, DB에 캐시 존재 시 즉시 6단계로 이동 |
| **2. 전체 구간 분할** | gemini-4-argon | low | 영상 전체 (오디오) | `[{start, end, label, title, summary}]` | 약 8분 | 재시도 1회 수행, 그래도 실패 시 에러 반환 및 처리 중단 |
| **3a. Song 처리** *(4개 병렬)* | gemini-4-argon | medium | 해당 구간 오디오 + 직전 talk 요약 | 줄 단위 정렬 배열 (시간, 가사, 번역, singer 등) | 약 14초 (곡당) | 부분 캐싱 후 해당 곡은 제외하고 다음 구간 진행 |
| **3b. Talk 처리** *(4개 병렬)* | gemini-4-argon | medium | 해당 구간 오디오 | 멘트 텍스트, 번역, 다음 곡을 위한 요약 | 약 10초 (구간당) | 기본 번역만 시도, 요약 실패 시 다음 Song에 빈 맥락 전달 |
| **4. 검증 루프** | gemini-4-argon | high | 구간 오디오 + 3a의 Song JSON | 오류가 수정된 최종 JSON (+ 검증 로그) | 1~2분 | 최대 2회 도달 시 루프 강제 종료, 마지막 상태 유지 |
| **5. 후처리** | -- | -- | 4단계 통과 JSON | 시간 보정(-0.5s) 및 겹침 제거된 JSON | < 1초 | 데이터 무결성 체크 후 손상된 줄 제거 |
| **6. 결과 저장** | -- | -- | 5단계 최종 JSON | DB 저장 및 클라이언트 반환 | < 1초 | 캐싱 실패 시 프론트에 결과만 바로 전달 |

## 2. 자율 싱크 검증 루프 (Validation Loop) 설계

Argon 모델 특유의 환각(실제 소리가 아닌 상황 추측)과 시간 지연을 잡기 위한 핵심 품질 관리(QC) 파이프라인입니다. (Song 구간에만 적용)

### 🔍 검사 항목 3개와 측정 방법

1. **큰 시간 오류 (Time Alignment Error)**
   - **기준**: 줄 시작 시간이 1.5초 이상 엇나갔는가?
   - **측정 방법**: Argon에게 전체가 아닌 해당 가사 줄의 시작 시간 기준 ±3초 구간의 오디오만 다시 듣게 한 뒤, "이 줄의 첫 단어 발성이 이 짧은 구간 내의 어디에서 시작되는가?"를 다시 핀포인트로 찍도록 지시.

2. **가창자 오표시 (Singer Mislabeling / 환각 방지)**
   - **기준**: `crowd` 또는 `both`로 라벨링된 줄이 실제로 관객이 부른 것이 맞는가?
   - **측정 방법**: 해당 구간을 들려주고 "이 구간에 관객(다수)의 목소리가 분명하게 들리는가? YES / NO / UNSURE 로만 답하라"는 매우 좁고 객관적인 질문을 던져 환각을 차단.

3. **누락 줄 복구 (Omission Check)**
   - **기준**: 라이브 오디오 상에서 실제로 불렀으나 텍스트 배열에서 빠진 구절이 있는가?
   - **측정 방법**: 곡 구간 전체 텍스트를 쭉 훑고, 전후 문맥상 오디오와 비교해 비어있는 타임라인이 있다면 누락된 가사와 번역을 삽입.

### 🔄 회차별 처리 흐름 및 제어
- **흐름**: 3a단계 결과물 수신 → [검사 1, 2, 3항목 순차 평가] → [오류 발견 시 즉각 JSON 수정 및 로그 작성] → [수정된 JSON으로 다음 회차 진입].
- **종료 조건**: 위 3개 검사 항목에서 오류가 0건으로 검출될 때, 또는 최대 2회 반복을 채웠을 때 루프 종료 (무한 루프 방지).

### 📝 회차별 진행 로그 예시 (SSE 스트리밍)
- `"회차 1: 37:36 구간 both → 관객 목소리 없음(NO) 판단 → artist로 교정 완료"` *(사전 테스트 환각 사례 교정)*
- `"회차 1: 12:04 구간 1.8초 지연 발견 → ±3초 재탐색 후 시작 시간을 -1.5초 앞당겨 재정렬"`
- `"회차 1: 누락 검사 → 2절 도입부(14:20) 1줄 누락 발견 → 원문 및 번역 추가"`
- `"회차 2: 21:51 구간 crowd → 관객 목소리 명확함(YES) → 라벨 유지"`
- `"회차 2: 44:10 구간 밴드 폭음으로 가창자 식별 불가(UNSURE) → 불확실 상태로 루프 종료"`

### ⚠️ UNSURE (불확실) 상태 처리
- 검증 루프가 끝까지 판단하지 못해 `UNSURE`로 남은 줄은 결과 JSON에 `is_uncertain: true` 플래그를 추가합니다.
- 프론트엔드는 이 플래그가 있는 가사에 희미한 노란 밑줄과 `[?]` 툴팁을 표시하여, 사용자에게 AI의 한계를 투명하게 공개하고 신뢰를 확보합니다.

## 3. 단계별 프롬프트 설계 방향

### 🎯 모든 프롬프트의 공통 최우선 규칙
> "실제로 들리고 보이는 것만 근거로 판단하라. '콘서트에서는 보통 이렇다'는 식의 추측은 엄격히 금지한다. 스튜디오 음원의 가사를 기억해서 쓰지 말고 라이브에서 실제로 부른 대로만 적어라. 판단 근거가 부족하면 임의로 채우지 말고 null 또는 UNSURE를 반환하라."

### [2단계] 전체 분할 (Segmentation)
- "입력된 라이브 공연 오디오 전체를 듣고 타임라인을 끊김 없이 분할하라."
- "각 구간을 song, talk, singalong, applause, credits, other 중 하나로 분류하라."
- "곡 제목은 영상 자막에 의존하되, 자막이 없으면 가사를 통해 유추하고 확신할 수 없으면 'Unknown song'으로 적어라."

### [3a단계] 곡 단위 처리 (Song)
- "제공된 곡 구간 오디오의 가사를 들리는 그대로 0.1초 단위의 타임스탬프와 함께 정렬하라."
- "영어로 번역할 때, 내가 context 변수로 제공한 '직전 멘트(talk)'의 요약을 바탕으로 곡의 감정과 배경을 반영하라."
- "가수가 마이크를 넘기는 순간은 `singalong_request`로 표기하고, 관객이 부른 부분은 `singer`를 `crowd`로 표기하라."

### [3b단계] 멘트 단위 처리 (Talk)
- "가수가 말하는 내용을 정확하게 받아쓰고 영어로 자연스럽게 번역하라."
- "이 멘트에 다음 곡에 대한 감정선이나 배경 설명이 있다면 2~3줄로 요약하여 `summary` 필드에 담아라."

### [4단계] 검증 루프 (Validation Loop)
- "너는 제공된 가사 JSON과 오디오가 완벽히 일치하는지 검수하는 역할이다."
- "특히 `crowd`/`both` 라벨이 붙은 구간은 '관객 목소리가 분명히 들리는가?'에 대해 YES/NO/UNSURE로 답하고 오표기를 수정하라."
- "시작 시간이 1.5초 이상 엇나간 줄이 있다면 해당 시간의 ±3초 오디오만 집중해서 듣고 재정렬하라."

## 4. API 사용 원칙

- **호출 방식**: Google GenAI SDK의 Interactions API를 사용합니다.
- **비동기 처리**: 전체 구간 분할(~8분) 및 검증 루프 등 응답이 긴 작업은 무조건 `background=True` 옵션으로 실행한 뒤, `interactions.get(id)`를 주기적으로 호출하여 결과를 폴링합니다.
- **파라미터 제한**: 공식 가이드에 따라 deprecated된 `temperature`, `top_p`, `top_k`, `thinking_budget`, `cached_content`는 코드 내에서 절대 사용하지 않습니다.
- **동시성 제어 (Rate Limit)**: API 호출 한도 및 1인 개발/서버 자원을 고려하여, 구간별 병렬 처리는 최대 4개 동시 호출(Concurrency Limit: 4)로 제한합니다.
- **재시도 로직**: API 호출 실패(503, 타임아웃 등) 시 즉각 종료하지 않고 Exponential Backoff(지수적 백오프) 방식으로 최대 1회 재시도를 수행하여 파이프라인의 탄력성을 확보합니다.
